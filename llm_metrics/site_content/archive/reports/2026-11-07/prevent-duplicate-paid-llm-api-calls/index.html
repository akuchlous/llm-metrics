Question

How do we prevent duplicate paid LLM API calls in scheduled benchmarks?

Archived edition, published 7 November 2026 (UTC). Read the current answer.

Answer

Our scheduled benchmark avoids duplicate paid LLM API calls by making each 15-minute time slot claimable exactly once. Before any paid request, the job creates a claim object for that slot in Cloud Storage with a create-only condition. Only the first creation can succeed. Any other run for the same slot sees the existing claim and stops without calling the provider.

A claimed slot is never retried, and a paid request is never repeated. If something fails after the claim, that slot stays empty rather than paid for twice.

These are controls on one code path, not a guarantee about total spend. The last section explains what they do not cover.

One atomic claim per time slot

The collector runs on Google Cloud Run, triggered every 15 minutes by Cloud Scheduler. Each run works out its slot, such as 18:00 or 18:15 UTC, from its own clock. It never takes the slot from an argument, and the command accepts no arguments at all.

The claim's object name is built from the mode, request profile, workload, origin and slot, for example …/claims/prod/openai.gpt-6-luna.v1/interactive-chat-v1/gcp-us-central1/2026-11-06/1800.json. It is written with Cloud Storage's ifGenerationMatch=0 precondition, which means "create only if no object of this name exists". The storage service enforces that rule itself, so two runs that start at the same moment cannot both create it.

After creating the claim, the job reads it back and checks that it is unchanged. It also compares the claim's creation time on the server with its own clock and refuses to continue if they differ by more than 120 seconds. When the claim already exists, the run logs a duplicate_skip event and exits without a provider call. When the claim attempt fails or its result is unclear, the run refuses to make the request.

The claim contains the attempt ID that the measurement record will use. A separate audit tool can therefore match every claim to its record and report any slot that was claimed but never recorded.

No retries of a paid request

Retries are a common source of duplicate charges, so the paid path has none:

  • Cloud Scheduler is configured with zero retries. A missed delivery is a missed slot, never made up later.
  • Each provider request is exactly one HTTP request. We call the API directly instead of through the provider's SDK, partly because the SDK retries by default.
  • Saving the measurement record retries only the storage write, a bounded number of times, and never repeats the provider request. By the time a record exists, the measurement is over.
  • A slot stays consumed after a crash, a provider failure or a failed write. A later run for that slot finds the claim and skips.

A fixed, bounded schedule

The collector can only run one fixed measurement: request profile openai.gpt-6-luna.v1, workload interactive-chat-v1, from Google Cloud. Nothing about the target can be chosen by the caller.

Its activation window comes from the job's configuration and must start on a quarter-hour and last exactly 24 hours, which allows exactly 96 slots. Missing, shorter, longer or misaligned windows are refused. The scheduler's identity may only start the job; it cannot change the window. A run that starts more than 7 minutes after its slot began is refused, and the window's end and the late limit are checked again immediately before the request.

Before claiming a slot, the job also checks that it can create and read objects in its results bucket and that overwrites are refused, so it does not spend money on a request it could not record.

How the controls are tested

The controls are covered by offline tests that use a simulated storage service and provider, so they cost nothing. In one test, eight runs for the same slot start at the same instant: exactly one provider call, one claim and one record result. In another, a delivery arrives every minute from 30 minutes before the window to 30 minutes after it: exactly 96 provider calls are made.

These tests show that the code behaves as designed against a simulated store. They do not prove how the real cloud services behave in every failure case.

What these controls do not guarantee

  • It limits this code path only. Anyone with owner rights on the cloud project could change the job, delete claims (which would reopen slots), change permissions or run other code with the same API key.
  • It limits requests, not money. Budget alerts notify us but do not stop spending.
  • A crash can lose a measurement. If the job stops after a paid response but before the record is saved, that request was paid for but not recorded. The audit reports it as a claim without a record. It is not retried.
  • Some slots are given up on purpose. An unclear claim result or a clock disagreement uses up the slot without a request. That reduces coverage in exchange for never paying twice.
  • It depends on the clock and the scheduler. Slot timing relies on the container clock, checked against the storage service's time, and on Cloud Scheduler delivering runs.
  • Not every cloud behaviour has been observed. The code handles both of the refusal responses Cloud Storage may return when an object already exists, but which one it actually returns has not been confirmed.
