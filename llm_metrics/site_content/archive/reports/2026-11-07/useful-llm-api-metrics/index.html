Question

Which LLM API metrics are useful, and why?

Archived edition, published 7 November 2026 (UTC). Read the current answer.

Answer

The useful LLM API metrics are the ones that describe what a caller actually experiences: how long until the answer starts, how long until it finishes, how fast text is generated, how often requests fail, and what each request costs. Each one needs its sample size, time window and setup next to it, or it cannot be trusted.

The metrics and why each matters

  • Time to first token (TTFT): how long until the first piece of answer text arrives. It is what people feel in chat and other streaming interfaces, and it captures connection time, queueing and prompt processing.
  • Total response time: how long until the whole answer has arrived. It matters for batch jobs, tool calls and structured output, where nothing is usable until the end.
  • Output tokens per second: how fast the answer is generated after it starts. It explains why long answers take longer, and it is only meaningful when the provider reports the output token count.
  • Reliability: how many requests succeed, and how the rest fail (for example rate limits, timeouts or server errors). A fast service that often fails is not fast in practice.
  • Token usage: input, cached input and output tokens as reported by the provider. These drive both cost and latency, so they are recorded rather than estimated from the text.
  • Cost per request: computed from the reported tokens and stored per-token prices. Estimated cost is not the same as billed cost, and the cost of a failed request is unknown rather than zero.

How to summarize them

Single requests vary, so latency is reported as percentiles over many requests. The median (p50) shows a typical request; the 95th percentile (p95) shows how slow the slow ones are. Averages hide slow outliers and are easy to distort.

Failed requests are counted separately and never included as fast latency values. Every published figure should state how many successful requests it is based on, the time window, the model, the prompt and settings, and where the requests were sent from.

What our benchmark records

Our open benchmark records each of these for one OpenAI model with one fixed workload from one Google Cloud region: TTFT, total response time, output token rate where the token count is known, success or failure with an error category, reported token usage including cached input, and an estimated cost from stored prices. No validated measurements have been published yet; when they are, they appear on the OpenAI TTFT metric page with their sample size and window. Actual project spending is tracked separately on Project costs.

Limitations

These metrics describe one setup. Results from a different prompt, answer length, model, region or account can differ, and providers change their infrastructure over time. Metrics measured from the client include network time, so they are not the provider's internal numbers.
