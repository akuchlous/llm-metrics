The collector runs on Google Cloud Run, triggered every 15 minutes by Cloud Scheduler. Each run works out its slot, such as 18:00 or 18:15 UTC, from its own clock. It never takes the slot from an argument, and the command accepts no arguments at all.

The claim's object name is built from the mode, request profile, workload, origin and slot, for example …/claims/prod/openai.gpt-6-luna.v1/interactive-chat-v1/gcp-us-central1/2026-11-06/1800.json. It is written with Cloud Storage's ifGenerationMatch=0 precondition, which means "create only if no object of this name exists". The storage service enforces that rule itself, so two runs that start at the same moment cannot both create it.

After creating the claim, the job reads it back and checks that it is unchanged. It also compares the claim's creation time on the server with its own clock and refuses to continue if they differ by more than 120 seconds. When the claim already exists, the run logs a duplicate_skip event and exits without a provider call. When the claim attempt fails or its result is unclear, the run refuses to make the request.

The claim contains the attempt ID that the measurement record will use. A separate audit tool can therefore match every claim to its record and report any slot that was claimed but never recorded.
