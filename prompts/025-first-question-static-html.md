# Step 025 — First question-driven static HTML analytics page, local only

**One micro-step.** Make one genuinely useful, accessible static HTML page from a Step 024 validated analytics JSON artifact. No hosting, cloud deployment, scheduled regeneration, dated-version alias, provider calls, or collector modifications in this step.

## Product direction
The website is **question-first**, not dashboard-first. The first page asks: **“How do you measure OpenAI API time to first token (TTFT), and what does our interactive-chat benchmark show?”** Structure: question/title -> concise answer -> method -> key findings -> metrics/dashboard-style evidence. Do not title it a broad “fastest model” ranking: we currently measure only one OpenAI profile, one fixed workload, one origin, and partial-day samples.

## Implementation
- Read Step 024 report, code/schema and validation tests first; only use the defined summary, never simulated examples in a production page. Create a deterministic local static site generator with a small template and minimal CSS, reusing the current Jinja/template infrastructure if appropriate **without** coupling it to live Flask or SQL. Output an `index.html` under a configurable local directory and a CSS asset. Generating HTML needs no HTTP service or GCS access. Use safe HTML escaping for all data and an appropriate Content Security Policy if feasible for static hosting.
- Article should explain measured TTFT boundary (first actual streamed token rather than first byte), fixed versioned prompt scenario (fictional Lumen Notes offline synchronization), requested output cap 300, `gpt-6-luna`/`openai.gpt-6-luna.v1`, `interactive-chat-v1`, explicit no reasoning, cache policy disabled, from GCP us-central1. Reflect actual code definitions; explain that we do not store prompt or response, grade answer quality, or know cross-provider rankings. The methodology and context should remain accurate even if today's numbers change.
- Evidence cards/chart/table from REAL validated Step 024 summary: TTFT distribution p50/p95, total latency, throughput, count, failures, date range, origin, token/cost summary with unknowns. Use accessible semantic HTML and, if useful, a static SVG or simple CSS bars based on factual values (no heavy client JS or untested third-party CDNs). Units, missing-values and low sample sizes visible; “No validated data” state rather than fake values; methodology/version and dataset fingerprint visible.
- Preserve clear separation: human-authored explanatory text vs numeric values rendered from summary. An automatic refresh must never silently rewrite an editorial conclusion or title when stats change. Tests cover escaping/XSS, missing fields, failure/no-data state, deterministic HTML, links, filenames, mobile readability/accessibility basics. Add local preview directions using a file browser or local static server; no public domain or route changes.

## Required SEO and Google AI-search-ready HTML
Review current official Google Search Central guidance: https://developers.google.com/search/docs/appearance/ai-features , https://developers.google.com/search/docs/appearance/structured-data/breadcrumb , https://developers.google.com/search/docs/appearance/structured-data/article and https://developers.google.com/search/docs/crawling-indexing/canonicalization . Google's AI Overviews/AI Mode need the same technical and helpful-content SEO foundations, **not special AI-only markup**. Do not add speculative `llms.txt`, artificial content splitting, keyword-stuffed text, or promise ranking/indexing.

- **HTML metadata:** semantic HTML5, lang=en, charset UTF-8, viewport, unique question-focused title, factual meta description, absolute HTTPS rel=canonical from validated configurable site URL/slug; matching Open Graph title/description/URL. Don't invent an image. One H1 with logical H2/H3 structure. Add descriptive internal links and a responsive mobile layout; retain all important metric facts as directly crawlable HTML text, not JS-only plots.
- **Breadcrumbs:** visible accessible linked Home > LLM Performance > TTFT navigation (`nav aria-label="Breadcrumb"`), with genuinely existing local destinations, and JSON-LD schema.org BreadcrumbList whose items/URLs exactly match visible links. Generate minimal parent pages if needed, not dead links. Meaningful HTML tables with headers, captions and units; optional charts supplement text.
- **Article structured data:** valid JSON-LD Article (or appropriate subtype), with true headline, canonical URL, visible dates, publisher/author only when verified. Supply datePublished/dateModified only when known; omit rather than invent. Dates for source measurement refresh are separate from editorial modification timestamps, which should not change on each generator run. Escape serialized JSON-LD so untrusted values cannot break out of `script` tags; ensure a considered CSP allows non-executable JSON-LD but blocks executable untrusted scripts. Never assert that schema guarantees rich snippets.
- **Answer-first content for searchers:** the first substantive section directly answers 'what is TTFT and how do we measure it?', then measured findings with sample count/range/caveats, then full measurement methodology, limitations and related questions. Distinguish streaming first-byte, first content chunk and first output token **using the real timer semantics in code**—do not invent higher precision. Describe fixed Lumen Notes workload, model/profile, request caps, reasoning/cache controls, GCP region, measured successes/failures, actual cost uncertainty and reproducibility. Human-written explanations and claims must stay separate from refreshed numeric fields.
- **Transparent provenance:** display validated dataset/source fingerprint, analytics schema, workload/profile IDs, methodology version (if a formal version is not yet defined, add an explicit accurate one rather than making one up), actual UTC collection window, sample count, data last-refreshed timestamp and preliminary/low-n limitations. Attribute authors and publisher only with known facts. Do not publish real-provider ranking from single-model data.
- **Offline SEO tests:** parse generated HTML/JSON-LD; check title/description/canonical/OG, one H1, valid and consistent BreadcrumbList + Article, visible breadcrumbs and working local links, readable metrics without JavaScript, correct provenance/dates/units, blank or malformed input, low-n/no-data rendering, HTML and JSON-LD/script-breakout XSS, no invented author/date/image, viewport and deterministic output. Record tests deferred to the live website (Rich Results Test, Search Console URL Inspection, sitemap and mobile performance).
- Step 025 is **local only**: create metadata/template interfaces compatible with the versioned/redirect publication of Step 026, but do not build redirects, public hosting, crawling controls or scheduler yet.

## Yoast-inspired SEO quality standard (no WordPress dependency)
Use Yoast SEO's **editorial and technical checks as a reference quality checklist**, alongside authoritative Google Search Central documentation—not as runtime code, a plugin, or a promise of Google ranking. Keep the site statically generated: no WordPress, PHP, WordPress database, headless CMS, Yoast API, or licensed plugin required. Explicitly check focus question/topic clarity, natural keyword use in title/intro/headings/slug/meta description (no stuffing), relevant descriptive internal links, readability, meaningful concise paragraphs, page intent, structured data, breadcrumbs and crawlable answer-first content. Record automated pass/warn/manual-review findings in the local build report; avoid pretending simplistic keyword or readability scores establish SEO success. The real strength is original measurement evidence and clear methodology.

**Prepare for changing answers:** treat the editorial answer/interpretation as **versioned content separate from metrics and methodology**. The page renderer must accept an explicit `answer_revision` identifier and editorial text as inputs; it must not infer/rewrite “the answer” from a new p50 alone. The visible page must distinguish “answer as of [measurement period]” from “data last refreshed.” Step 026 will own immutable answer history, editorial review and dated publication; Step 025 should only define and test the metadata interface. A materially changed conclusion (e.g., fastest model changes after more providers are measured) requires a new reviewed answer revision, not a silent numerical update.

## Acceptance
A developer can run offline fixture -> analytics JSON -> one readable static HTML page and inspect real-style charts without any hosted app, SQL, GCP or paid provider call. Report exactly which parts were based on synthetic test data vs actual verified data; **do not claim production launch**.
