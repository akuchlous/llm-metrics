# Step 028 — Weekly cloud publication for metrics Q&A and full-project charged-cost transparency

**One focused step.** Following reviewed Steps 026–027, build a controlled **once-per-week** cloud-triggered publication workflow for *existing reviewed* metrics-related Q&A pages, their linked metric pages and the top-level /costs transparency page. Preserve independent educational publishing. This step must not alter Step 023 collector or trigger any paid LLM measurements. **No automatic LLM-generated prose or unsupported answer revisions.** Cloud creation, deployment, scheduler enabling, billing access and paid activities require fresh explicit scoped approval in the executing session.

## Product goals and publishing policy
- Every week, a cloud scheduling trigger (prefer a simple GCP Cloud Scheduler -> short-lived Cloud Run Job/batch publisher, after verifying currently available hosting/IAM/cost) checks for **new validated analytics snapshots**. On meaningful new data, regenerate the *data portions* of relevant metric detail pages and Q&A citations/factual evidence while retaining each Q&A's reviewed answer revision and human-authored explanations. Do not regenerate the same article/date solely because a cron tick occurred. Publish **new dated immutable edition** only when policy criteria support one; never rewrite archived HTML. Use Step 026's question IDs, current hubs, dated /reports/YYYY-MM-DD/... versions and Step 027's static hosting/SEO contracts.
- **Weekly cadence default:** Sunday 02:00 UTC (configurable in UTC); one execution per weekly interval, no catch-up paid LLM calls, safe replay/no duplicate edition if trigger retries. Treat scheduling as *publication only*, not a new collection authorization. Explicitly choose the last fully validated, auditable UTC measurement window and show the data through date on each page. If no fresh validated data, leave metric publications and metrics-related Q&A answer text unchanged and record "no change". If records are missing/incomplete or stale, hold the metric update and report the precise gap. Educational Q&A publishing remains available at any time.
- **Editorial review gate:** a metric change may warrant different answer wording or ranking. The job must **not auto-approve, rewrite or promote a changed substantive answer**. It may produce a machine-readable "answer review needed" candidate/report with evidence and notify operator; approved editorial revisions are a separate explicit action. Non-substantive data-card refreshes can be published according to approved policy. If a page contains a hard-coded factual claim invalidated by new numbers, block that page's update until review rather than silently serving a contradictory claim. No speculative "which model is fastest" ranking when population insufficient.
- **Cost of weekly workflow itself:** measure and account for scheduler invocations, Cloud Run execution, storage/egress, static hosting build/deploy, any billing export jobs and explicitly authorized third-party services. Publish this under **weekly publishing operations**, separately from LLM model-call charges, with actual billed charges reconciled later. Do not mistake modeled GCP charges or billing estimates for cash charges.

## Permanent total-cost transparency
The top-level user-facing question is **"How much have I actually been charged to operate the entire LLM Xchange project, across all providers and services, since the project began?"** This is a lifetime **real charges** accounting task, not a formula over benchmark usage. Cover every known project expense source: OpenAI/Anthropic/Gemini/xAI as applicable, GCP Cloud Run/Scheduler/GCS/network/other resources, hosting/CDN, domain registration, and any paid developer/operations SaaS or tooling attributed to the project. Exclude unrelated expenses and separately label optional opportunity cost (labor). Start the reporting period at a documented, operator-approved project inception date. Provide per-source coverage ranges and reconcile historical charges, not only the current week.

- **Source of truth for charged actuals:** authorized invoices, card/payment records and provider billing statements/exports. Keep usage-based provider dashboards as *estimates* until reconciled against actual billed or charged amounts. Separate **paid/charged**, **invoiced but unpaid**, **accrued/unbilled usage estimate**, **credits/refunds/taxes** and **unknown/unconnected**. Clarify whether 'charged' means net card/actual settled charges; if provider invoices and bank statements differ, document which reconciled source wins. Include invoice/payment identity in the private ledger for deduplication, never in public HTML. Billing lags are expected: show a last-verified UTC timestamp and how far each source is reconciled.
- **Prevent double counting:** overlap across GCP consolidated billing versus per-resource usage, provider dashboard estimates versus paid provider invoices, retries/voids/refunds, multiple accounts, and transactions spanning weeks. Deduplicate by stable private source identity, allocate multi-period charges consistently, account for credits and refunds explicitly. Avoid summing different currencies as though they are USD; report native currency totals, and only provide an aggregate converted figure using documented verified dated FX sources and policy.
- **Truthful total:** show a single lifetime total actually charged **only if all identified source accounts/vendors and the full claimed history are reconciled**. Otherwise prominently label the result **verified charged subtotal (incomplete)** and list missing vendors/date ranges/other uncertainties; mark the true total "not yet verified". Never silently treat missing accounts as zero, extrapolate 24h API experiment charges to lifetime spend, or invent project invoice amounts. A verified 0 needs evidence.
- Publish a factual **weekly cost update** independent of analytics updates (as long as vetted new billing evidence exists): charged in the latest verified reporting period, cumulative paid/charged amount or verified subtotal, service breakdown and the cost of the **weekly publishing job** itself. A dated /reports/YYYY-MM-DD/project-costs edition retains its as-of cut-off, source hash manifest, calculation revision, period, editorial approval and methodology; an unchanged week creates no new edition. If billing inputs are absent, show a stale/unknown disclosure and **do not** issue a false cost update. Cost Q&A links to relevant methodology, model API pricing and per-experiment cost articles.
- **Billing integration choice:** start with a deterministic manual import/reconcile format. Optionally propose least-privilege GCP Billing export and relevant provider billing connectors; **no access/install/API billing action without user approval**. If a vendor lacks an API or export, permit manual verified receipts and keep it on an explicit coverage checklist. Do not leak billing details into public build artifacts. Do not grant the website runtime access to billing data.

## Implementation phases
**Phase 0 (offline, no approval needed):** read existing Steps 024–027 implementation, schema and actual site release manifests; design and test a weekly publisher CLI in dry-run mode with local fixture analytics and private cost-ledger fixtures (synthetic and labeled); deterministic UTC slot calculation, no-change/changed-data logic, approval gating, data hash and cost-source validation, private/public separation, durable run record, atomic publish plan and rollback. Verify dry-run does not access GCS/provider APIs or connect to billing. Produce a concrete minimal GCP architecture, pricing estimate with assumptions and a permissions diff. Prefer direct reuse over a new Flask service, database or complex queue.

**Approval A (fresh, in-session, bounded):** create a staging-only weekly execution workflow and read-only access to *approved sanitized* inputs using narrowly scoped IAM; do not access private billing provider accounts without separately scoped approval. Verify scheduler duplicate invocation behavior, at-least-once dispatch idempotency, immutable edition creation, unchanged-run no-op, failure/rollback, logs sanitized, and cost metering. Prefer no always-on resources. Set explicit operator budget/alert policy and acknowledge alert != spending cap.

**Approval B (fresh and separate):** enable weekly production trigger after operator checks staging, initial reviewed content, current host URLs, confidential billing-data isolation, rollbacks, actual spend forecast and event monitoring. Do not assume user owns DNS or billing identities. Document how to pause/disable publication immediately, scheduler ownership, recovery/retries, audit trail, and publishing job spending in /costs once actual bill evidence arrives. No schedule enabled by default.

## Tests and acceptance
- A weekly simulated run with new verified analytics creates updated factual metric evidence, preserves reviewed Q&A answer text, and publishes only appropriate immutable snapshots and current pointers; reruns do not duplicate. No data/invalid/partial data keeps last approved published pages and reports accurately.
- A new dataset that would invalidate the current answer generates **review required**, not an unreviewed answer; manual approval produces a new dated answer edition with immutable old one. Cross-link integrity between Q&A, metrics and dated snapshots holds; home, /questions, /costs and sitemap update atomically as necessary.
- Offline cost fixtures cover full settled billed history vs partial history, multiple billing accounts, repeated vendor charges, invoices vs card charges, refunds, tax, credits, unknown service, cross-currency conversion, overlapping periods, late charges, weekly job expense and stale input. No false global total. A missing billing source blocks any total-completeness claim, **not** independent educational publication.
- Publishing cost itself is shown as **verified charge or pending reconciliation**, not a fabricated dollar figure. Public artifacts exclude account IDs, payment records and private provider secrets.
- No Step 023 changes, no new provider API calls, no live billing reads or actual cloud changes without fresh approval. Preserve project target ≤ $10/day (budget alerts are not hard spend caps).
