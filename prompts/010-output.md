# Step 010 — Implementation report

Prompt: `010-token-accounting-and-cost.md`.

## What changed

- **Provider interface:** `stream(prompt, max_output_tokens)` yields text chunks, then exactly one `Usage(input_tokens, output_tokens)`, the way real APIs report usage in a final event.
- **`DummyProvider`:** uses a **simulated tokenizer** (`ceil(len(text)/4)`) and stops before exceeding the cap.
- **`measure_request`:** returns `(request, results)`. `request` holds the token facts from `Usage`; `results` are the metrics, unchanged in meaning, with total latency now listed first. It fails on missing or duplicate usage, or output above the cap.
- **New `llm_metrics/pricing.py`**, the only place prices live: dummy simulated $2.00 / $8.00 per 1M tokens (USD), plus the `request_cost()` formula.
- **Schema version 2:** a new `requests` table (llm-metrics UUID id, tokens, cap, effective prices, unrounded costs), plus `observations.request_id`. `save_request` writes the request and its observations in one transaction with one timestamp.
- **Transactional upgrades:** schema upgrades now run in one `BEGIN IMMEDIATE` transaction.
- **CLI** prints tokens and cost labelled "(simulated)", and the request id.
- **New `/requests` view:** the 20 most recent test requests, with total latency first and TTFT as a diagnostic. Both views share a nav. The aggregate view is unchanged (default metric still `ttft`).

## Schema / data-model decisions

- **Request facts are not metric rows.** Tokens, the cap, prices and costs describe the request; they aren't per-metric measurements. Storing them as `metric/value` rows would mix units and pollute metric queries, so they live in `requests`. The metrics stay in `observations`, linked by `request_id`.
- **Request identity:** a random UUID (hex) generated by llm-metrics, never a provider ID. UUIDs, not integers, so databases from different machines can be merged later.
- **No fabricated values:** pre-Step-010 observations and seeded history keep `request_id` NULL, and the upgrade creates no `requests` rows.
- **CHECK constraints** on token counts, cap ≥ 1, non-negative prices, and environment.

## Token-count semantics

- `input_tokens` and `output_tokens` come **only** from the provider's `Usage`, in the provider's own token units. They are never counted from chunks: the dummy streams 5 chunks but reports 7 output tokens, and tests cover chunks of 1 vs 3 tokens.
- `requested_max_output_tokens` is the cap the benchmark asked for (`MAX_OUTPUT_TOKENS = 64`); `output_tokens` is what was generated (7). They're stored separately, and measurement rejects `output_tokens > cap`.
- **Simulated tokenizer:** 1 token per 4 characters, rounded up; "Say hello." is 3 input tokens. It's deterministic for tests and does not match any real provider.
- **No `output_tokens_per_s`:** there's no per-token timing, so `output_chunks_per_s` is kept unchanged.

## Pricing / cost semantics

- USD per 1,000,000 tokens, keyed by (provider, model), in `pricing.PRICES` only. An unknown model raises a clear `KeyError`.
- `input_cost = input_tokens × input_per_1m / 1e6`; `output_cost = output_tokens × output_per_1m / 1e6`; `total_cost = input_cost + output_cost`. Example: 3 × 2 / 1e6 + 7 × 8 / 1e6 = $0.000062.
- Stored as unrounded REAL. Display rounds to 6 decimals.

## Historical-price decision

Each request stores the effective `input_price_per_1m` and `output_price_per_1m` alongside its costs. A test changes `PRICES` in code and shows the stored rates and costs are unchanged, and that the stored rates alone reproduce the stored cost. There's no price-history service or table, which isn't needed until prices are managed outside the code.

## Known limitations / review questions

- **Aggregate default:** the aggregate view's default metric is still `ttft` (preserving existing behaviour, and it's the only metric with history). Should the default become `total_latency`, given it's now the primary latency?
- **Float costs:** costs are floats. That's fine at these magnitudes, but sums over millions of requests may need `Decimal` or integer micro-dollars later.
- **One currency:** USD is implied by documentation; there's no currency column.
- **Pairing:** seeded and pre-010 observations can't be paired with requests (by design).
- **Upgrade backup:** there's still no automatic backup before an upgrade (noted in Step 09's design questions).

## Design Q&A

**Why a `requests` table instead of storing tokens and cost as more metric rows?** `metric/value` rows mean "a measurement in the metric's unit". Token counts and costs are facts about a request, and the cap is a configuration value, not a measurement. Putting them in `observations` would make "all metrics" queries return tokens and dollars, and pairing them back to their request would still depend on timestamps. A request row keeps one coherent record, and the observations keep their aggregate queries unchanged. *Tradeoff:* two tables and a join for the per-request view.

**Why report usage as the last stream item instead of a separate method or attribute?** It's stateless (no "last call" attribute that breaks under concurrency) and matches how real streaming APIs deliver usage (a final event). Measurement reads it in the same single pass. *Tradeoff:* the stream yields mixed types (`str | Usage`), so consumers must check types.

**Why store the rates when the cost is already stored?** The cost alone can't be explained or audited; with the rates and token counts, anyone can recompute it. If a price changes, old requests keep their own basis, and new ones get the new price. *Alternative:* a price-history table with effective dates, which is more machinery than one hard-coded simulated price needs.
