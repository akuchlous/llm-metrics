# Step 026 — Immutable dated versions and stable latest for static question pages

**One micro-step.** On the Step 025 local static HTML generation system, add safe, testable revision/version publication on the local filesystem only. Do not deploy a domain, schedule cloud jobs, modify collector, or regenerate prose via an LLM.

## Dual publishing surfaces (question pages and metric pages)
Extend versioned publication to the two Step 025 page types without coupling their revision cadence. Question article canonical: `/how-to-measure-openai-ttft`; evidence/TTFT canonical: `/metrics/openai/ttft`. Metrics pages are **first-class directly reachable landing pages**, not only embeds in a Q&A; their headline, description, structured data and breadcrumbs describe the factual metric, not the editorial question. Every Q&A page may cite a metric page; a metrics page should link to relevant methodology/Q&A. Build/validate the pair atomically when cross-link targets are required, without forcing an answer revision when only metric observations change.
Date-first immutable snapshots apply to **both surfaces**: `/reports/YYYY-MM-DD/how-to-measure-openai-ttft` and `/reports/YYYY-MM-DD/metrics/openai/ttft` (with `/r2` suffix if a same-day revision is required). Each snapshot preserves its own validated evidence and generated facts. Maintain stable current canonical URLs and optional `-latest` aliases without contradictory redirects/canonicals; dated snapshots remain accessible. A Q&A snapshot should cite an immutable metric snapshot for the exact underlying dataset when available rather than silently linking only to today's different numbers; current pages can link to current metrics and show the data window. Never publish a broken reference to an archive that was not produced.
Keep independent **dataset version**, **answer revision**, and **metric-page publication version**; analytics-only updates can publish new metrics snapshots without rewriting the approved Q&A answer, while publishing the updated Q&A data section/snapshot is optional according to explicit publication policy. Update release manifest to include page kind (`question` / `metric`), related-page links and exact supporting dataset hash, and test referential integrity across historical releases. Implement only a **minimal file-based question registry** in this step, not a database or CMS; this is necessary for stable question identity and history.

## Question registry, immutable editions and browseable history (required)
Create a **minimal file-backed question registry** (YAML, JSON or existing repository conventions) keyed by stable opaque `question_id`, with the canonical question title/slug, aliases (only verified same intent), related metric page IDs, and a pointer to the latest **approved** edition. Do not use exact question text or a changing title as identity. A semantic near-match is not automatically an alias: TTFT versus end-to-end latency, different workload or region can be a materially different question. Resolve ambiguous duplicates through explicit editorial review; don't automatically merge or redirect distinct user intents. Keep the registry lightweight, validated and dependency-minimal.

Store each answer edition as an **immutable content record**, with question_id, UTC publication timestamp, revision discriminator, exact reviewed answer/editorial text or a content-addressed immutable source, status/approval, evidence links, dataset SHA (if applicable), methodology version (if applicable), summary of what changed, and a source/commit reference for architectural claims. **Educational Q&A without any metrics data must be publishable**: dataset fields are optional for non-empirical articles, and absence of benchmark evidence must not block a sourced engineering/methodology answer. Only metric-bearing statements require corresponding validated data and provenance. A no-change rebuild must create no new edition. A changed answer creates a new edition; updated measurements with unchanged answer may create a metrics snapshot without forcing an answer edition.

Generate a **local chronological home feed** listing published editions newest-first (the same question may appear multiple times with distinct dates and contextual blurbs), a **/questions** directory grouped by stable question identity (one hub entry per question), and a **question hub** at the stable canonical slug showing the latest approved answer, edition timeline, related methods/metric pages, and a clear link to each immutable dated edition. Reuse the original Step 025 canonical question path rather than introducing a second competing canonical route; `/questions` is the directory, not a mandatory `/questions/<slug>` duplication. Include distinct SEO metadata and breadcrumbs for home, directory, hub, and editions. If Step 025 has already created a homepage, extend it rather than replace it; inspect its implemented structure first.

Historical `/reports/YYYY-MM-DD/<slug>` (and `/r2`) pages are immutable in **bytes**, including editorial content and links. To discover later editions, readers navigate via the stable question hub or regenerated /questions directory; do **not** modify old HTML to inject newer-edition links. At release time, an edition may link to older existing editions and to an immutable supporting metrics snapshot. The hub/index can point from old to new without touching archive artifacts. Show a visible 'Published on [UTC date]' and, on newer editions, 'What changed?' based on reviewed real differences—not algorithmic speculation.

SEO: near-identical dated versions should generally canonicalize to the stable question hub and be excluded from sitemap; genuinely distinct, substantive historical analyses can be self-canonical and selectively indexed under documented content-based criteria. Preserve browseability regardless of indexing. Avoid hundreds of low-value, duplicate date pages solely to target searches. All routes and cross-links must resolve locally; validate no orphaned edition, slug collision, duplicate question ID, missing approved target, unsafe route, wrong date, mismatched dataset reference or inconsistent release manifest.


Choose a permanent canonical human-readable question slug, initially `/how-to-measure-openai-ttft`. `/how-to-measure-openai-ttft-latest` is a stable **alias/redirect** to the canonical latest page. **Dated revisions use a date-first hierarchy**: `/reports/YYYY-MM-DD/how-to-measure-openai-ttft` (e.g., `/reports/2026-11-07/how-to-measure-openai-ttft`). The date means the **UTC publication date of that version**, not necessarily the measurement date; display the underlying UTC data window separately. If two distinct publications occur on the same UTC date, use `/reports/YYYY-MM-DD/how-to-measure-openai-ttft/r2` (and r3, ...), preserving `/reports/YYYY-MM-DD/how-to-measure-openai-ttft` as immutable revision 1. Never replace any prior dated page. A dataset-only refresh can create a dated snapshot while retaining the existing reviewed answer revision; a materially changed answer requires its own approved answer revision. URLs and redirects must work on the eventual static host; if host-specific redirects are required, generate a host-neutral redirect plan/metadata and an offline-testable stub, not assumptions about an undeployed service. Prefer one canonical indexable URL, avoid indexable duplicates, link historical revisions and identify immutable historical copies appropriately.

No blanket archive noindex or contradictory sitemap/canonical/redirect/robots hints. - Provide **explicit local URL-to-filesystem route mapping** for extensionless clean paths (e.g. slug/index.html, reports/YYYY-MM-DD/slug/index.html and reports/YYYY-MM-DD/slug/r2/index.html) and show that all URLs resolve in a static preview. Do not assume every static host understands filesystem rewrites; record required redirects for 027 without falsely implementing a production host. Reject malformed site URL, inconsistent metadata URLs and orphaned/broken internal links.
- Tests cover the exact date-first URL shape, UTC date boundary and the distinction between publication date vs data window; same-day /r2 snapshots; immutable archive bytes; archive vs latest canonical handling; 301/308 alias plan; previous-version navigation; XML-safe URL handling later; redirect loops; missing archive targets; metadata/date consistency; failed promotion leaving old canonical intact; and deterministic reruns.

## Answer versioning (separate from dataset refresh)
A question's **answer can genuinely change** as models, benchmark evidence or scope change. Preserve the exact answer published at each historical snapshot, not just the chart numbers. Define `answer_revision` (independent of article/editorial copy revision, dataset hash, methodology revision, workload/profile versions) and store the human-reviewed answer text or its immutable content hash, reviewed/published timestamp (when known), and supporting dataset reference in the release manifest. An update that changes only numeric metrics may refresh the canonical page without asserting a new substantive answer. A change to the answer's ranking, recommendation or conclusion must be explicitly reviewed, assigned a new revision, and published as a new immutable dated snapshot with provenance.

Each dated snapshot must preserve its original **answer wording, data window, supporting evidence, methodology, headline claims, and publication metadata**, even if today's canonical answer contradicts it. The main canonical question URL always presents the latest **approved** answer, not automatically the latest unreviewed aggregate. Include a clearly visible “Answer updated” indication and a “Previous answers”/“How the answer changed” trail when revisions occur. Tests: same dataset with editorial revision; newer dataset without answer revision; changed answer revision with old snapshot retained; interrupted promotion; canonical/latest pointer never exposing unreviewed claims. Keep the SEO duplicate/canonical policy from above consistent with meaningful standalone historical answers.

## Version every dependency
- Keep independent identifiers for workload version, request profile/model, **measurement methodology version**, analytics dataset version/fingerprint and article/editorial revision. Publishing a new dataset must not silently bump methodology or reword a qualitative claim.
- Generate a canonical release manifest `llm-metrics.publication.v1`: question slug, UTC publication date, source analytics SHA-256, exact aggregate window and validated counts, method version, article revision, output HTML/CSS hashes, and immutable source record manifest fingerprint. Include an explicit input/source validation gate (refuse invalid/unknown/incomplete or mixed real/test data) and a configurable sample threshold; label below-threshold outputs as draft and **do not** promote them to latest. The threshold is a publication policy, not a guarantee of statistical significance or a permission to claim best/fastest.
- Implement local **build -> validate -> stage -> promote**. Write the immutable dated version before the stable latest pointer changes; if any check fails the old latest remains intact. Replay of identical input should be idempotent; changed content on an existing immutable snapshot must refuse or allocate `-rN`, never overwrite. No accidental mutation/deletion of old releases. Validation tests include interrupted promotion, same-day retries/updates, changed data, no-change runs, invalid path/slug, absent snapshots, and consistent latest alias.
- Add “Previous versions” links and last-data-refresh metadata. Keep HTML generation text-editorial static, data-driven metrics refreshed independently. No cloud upload/deploy in this step.
