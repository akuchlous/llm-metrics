## Goal

One command builds a self-contained local app + PostgreSQL test environment, runs the actual tests, migrations and simulated benchmark, exposes a localhost dashboard, and cleans up **all project Compose containers, network and disposable volumes** on exit/Ctrl+C/failure. No host Python virtualenv, pip dependencies, PostgreSQL installation or background service is required. A developer without Docker gets a clear prerequisite error. Google Cloud Shell (where Docker is present) is the environment for runtime validation.

## Implement

1. Add minimal `compose.yaml` and a purpose-built local/test Dockerfile or build target (production Dockerfile must remain clean and functional). Include tests, migration files, scripts and hash-pinned dependencies in local test build; production image should not acquire test sources, Git history or secrets. Use only app/test-runner and official PostgreSQL, unless evidence proves another service necessary. Use project-scoped disposable volume or tmpfs, service DNS, health check, least privilege and no externally exposed DB.
2. **Rewrite `./run.sh` as the canonical Docker wrapper.** Default `./run.sh` should perform full offline tests **including actual PostgreSQL integration tests**, migration validation, simulated history seed + simulated measurement, and start a dashboard until Ctrl+C. Dashboard host mapping defaults to 127.0.0.1 and a configurable host port. It must reliably handle foreground signals, errors, failed tests and dashboard startup failure, cleaning project-specific Compose resources on every path. `./run.sh test` should perform equivalent tests, migration, simulated measurement and an HTTP 200 dashboard smoke, then automatically clean up. Optionally `./run.sh down` to recover after SIGKILL, with safe project scoping.
3. `./run.sh` must require `docker` and `docker compose` and display a helpful error if absent; **do not** silently use native Python/`.venv`. Do not add a separate Docker-only workflow as the primary interface. Document the prerequisite and both commands in README. Host may have Docker images and cache after the run; this is normal unless a safe explicitly targeted removal command is used.
4. The app/test environment must be offline for real providers: `APP_ENV=test`, no real API key injection, no `--real`, no paid requests, no Cloud SQL or real GCP mutations. Tests should have a disposable `TEST_POSTGRES_URL` pointed at the Compose PostgreSQL test DB. Ensure outside/inherited `TEST_POSTGRES_URL`, origin or application DB environment cannot redirect destructive SQL to a host/production database.
5. **Audit commit `a20bf6f` carefully.** Its integration test cleanup uses `pg_terminate_backend` and `DROP DATABASE`: fail closed unless the database is positively identified as a disposable Compose-owned test DB. A forwarded localhost port alone is NOT proof. Prefer allowing Compose to own cleanup of the isolated instance/volume rather than broad database deletion. Add focused safety tests and preserve tests' useful database correctness checks. Do not stop/disable local PostgreSQL through systemd; do not delete unrelated host databases/users.
6. Preserve the real-cloud safety guard from 018h (non-local paid commands require explicit PostgreSQL URL), provider/model exactness, workloads, measurement/TTFT and token facts, source pricing, unknown-vs-zero semantics, atomic persistence and simulated/prod separation. No unrelated refactors or public web infrastructure.
7. Verify using **real Docker** (Cloud Shell if needed): two fresh `./run.sh test` cycles with accurate total/passed/skipped counts; real PostgreSQL migration and integration cases actually executed; dashboard HTTP 200; default `./run.sh` can be interrupted and cleans up; test-failure cleanup proven. Inspect project-scoped Compose containers, network and volume before/after. Do NOT use global Docker prune or delete shared images. If runtime Docker unavailable, mark integration **UNVERIFIED**, and do not claim success.
8. Keep execution work in this step local/Cloud-Shell-hosted development only: no paid provider API calls, no GCP resource creation/builds/deployments, no new scheduler, no new providers, no public service. The Cloud Run Job image remains old and MUST NOT be executed. Target cloud spend < $10/day remains, but this step should generate no GCP/proprietary-model usage charges.
