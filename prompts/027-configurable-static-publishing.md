# Step 027 — Configurable daily/three-day static publishing, gated cloud release

**One micro-step.** Add a deliberately minimal operating path to regenerate and, **only after fresh explicit approval**, serve the Step 026 immutable question pages to web users. Do not touch collector cadence, paid API scheduling, existing GCS record immutability or benchmark security controls. **Do not purchase/register a domain or assume DNS credentials.**

## Two complementary static site sections
Publish two independently usable and internally linked sections: (A) **Question-and-answer** articles with reviewed explanations and versioned conclusions, and (B) **dedicated metric pages** with factual, regularly refreshed analytics. Minimum initial routes: `/how-to-measure-openai-ttft` and `/metrics/openai/ttft`, alongside date-first immutable `/reports/YYYY-MM-DD/... ` snapshots. A question page must link to its relevant metric evidence; each metric page must link to one or more genuine explanatory/methodology pages. Provide distinct SEO metadata, breadcrumbs and sitemap entries for both **canonical** page types, and make metric page tables/chart contents directly crawlable. No fabricated comparison, chart or URL; an additional metric page is generated only when supported by real validated data and an actual template.
The **metrics data-refresh cadence** can be daily/every three days/weekly independently of human approval of changes to a **question's substantive answer**. Any new claim, ranking or changed recommendation remains editorial-review-gated; never let an automatically regenerated metric page turn into unreviewed ranking prose. Preserve the exact snapshot dataset and answer relationship through immutable report URLs. No real-time dashboard server or SQL required.

## Independent knowledge publishing and chronological discovery
Deploy the Step 026 **question registry and immutable answer editions** as a first-class site feature. The homepage is a chronological publication feed (not a unique-question list), so repeated questions appear with their **own publication date, contextual revision label and distinct report URL**. `/questions` is a grouped-by-question directory, each stable question hub shows the latest *approved* answer plus its historical timeline; every dated edition remains accessible at `/reports/YYYY-MM-DD/<slug>` or `/r2`, without rewriting old HTML. Readers discover new answers via regenerated home/directory/hubs and archived editions via those hubs. Add cross-links from Q&A to related metric detail pages, and metric pages back to actual relevant Q&A; never generate dead-link placeholders.
**Critical independence:** sourced educational engineering/methodology Q&A can be approved and published **when there is no analytics JSON, no recent measurements, or the collector is offline**. Its release pipeline must not invoke Step 024 analytics or require GCS access. Metrics pages/data-bearing claims require validated analytics; if missing or incomplete, skip only affected metric refresh, keep previous metrics content intact, and continue safe approved Q&A publication. Failure of the metrics refresh must not roll back an unrelated valid educational article. Support editorial-triggered releases independently of scheduled metrics refreshes, with explicit approval and dry-run checks.
Keep the current homepage question hub and metrics routes consistent with the static server's clean-path mapping, including link crawl and breadcrumb checks. Sitemap should include home, /questions, current question hubs and current metric canonical pages; include individually self-canonical substantive historical editions only by documented SEO policy. Never list aliases or near-duplicate editions as additional canonical landing pages. Maintain separate meaningful change times for the feed, question hub, editorial answer and metric dataset. Version/approval metadata must not be confused with a timer tick.

## Yoast-style release checks and controlled answer updates
Keep the deployed product a **static HTML publishing website**; use Yoast-inspired checks as a CI/reporting standard, **not WordPress or Yoast runtime integration**. Apply per-page checks for query intent, title/slug/meta-description relevance, natural on-page terminology, answer-first readability, breadcrumb and internal link integrity, structured data consistency, sitemap/canonical/robots alignment, and real measurement provenance. Distinguish machine-verifiable checks from editorial human review. Do not chase arbitrary SEO “green light” scores or generate spammy near-duplicate question variants.

**Two independent update lanes:** (1) scheduled **data refresh** (daily/every-three-days/weekly) updates validated numbers/figures without silently changing human-authored conclusion or `answer_revision`; (2) **editorial answer revision** after human review changes the answer/recommendation if new data warrants it, creates an immutable dated revision, and atomically promotes the canonical/latest link. The live canonical answer must never point to unapproved newer claims. Provide a release note or concise 'what changed' description between substantive answer revisions, and link past answers with dates/dataset evidence. Test no-change runs, data-only updates, changed conclusions awaiting approval, successful human-approved publication, and rollback to the previous verified release. Keep publishing frequency independent of paid benchmark collection.
