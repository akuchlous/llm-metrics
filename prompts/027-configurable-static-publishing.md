# Step 027 — Configurable daily/three-day static publishing, gated cloud release

**One micro-step.** Add a deliberately minimal operating path to regenerate and, **only after fresh explicit approval**, serve the Step 026 immutable question pages to web users. Do not touch collector cadence, paid API scheduling, existing GCS record immutability or benchmark security controls. **Do not purchase/register a domain or assume DNS credentials.**

## Two complementary static site sections
Publish two independently usable and internally linked sections: (A) **Question-and-answer** articles with reviewed explanations and versioned conclusions, and (B) **dedicated metric pages** with factual, regularly refreshed analytics. Minimum initial routes: `/how-to-measure-openai-ttft` and `/metrics/openai/ttft`, alongside date-first immutable `/reports/YYYY-MM-DD/... ` snapshots. A question page must link to its relevant metric evidence; each metric page must link to one or more genuine explanatory/methodology pages. Provide distinct SEO metadata, breadcrumbs and sitemap entries for both **canonical** page types, and make metric page tables/chart contents directly crawlable. No fabricated comparison, chart or URL; an additional metric page is generated only when supported by real validated data and an actual template.
The **metrics data-refresh cadence** can be daily/every three days/weekly independently of human approval of changes to a **question's substantive answer**. Any new claim, ranking or changed recommendation remains editorial-review-gated; never let an automatically regenerated metric page turn into unreviewed ranking prose. Preserve the exact snapshot dataset and answer relationship through immutable report URLs. No real-time dashboard server or SQL required.

Readers discover new answers via regenerated home/directory/hubs and archived editions via those hubs. Add cross-links from Q&A to related metric detail pages, and metric pages back to actual relevant Q&A; never generate dead-link placeholders.

Failure of the metrics refresh must not roll back an unrelated valid educational article. Support editorial-triggered releases independently of scheduled metrics refreshes, with explicit approval and dry-run checks.

Version/approval metadata must not be confused with a timer tick.

## Yoast-style release checks and controlled answer updates
Keep the deployed product a **static HTML publishing website**; use Yoast-inspired checks as a CI/reporting standard, **not WordPress or Yoast runtime integration**. Apply per-page checks for query intent, title/slug/meta-description relevance, natural on-page terminology, answer-first readability, breadcrumb and internal link integrity, structured data consistency, sitemap/canonical/robots alignment, and real measurement provenance. Distinguish machine-verifiable checks from editorial human review. Do not chase arbitrary SEO “green light” scores or generate spammy near-duplicate question variants.

**Two independent update lanes:** (1) scheduled **data refresh** (daily/every-three-days/weekly) updates validated numbers/figures without silently changing human-authored conclusion or `answer_revision`; (2) **editorial answer revision** after human review changes the answer/recommendation if new data warrants it, creates an immutable dated revision, and atomically promotes the canonical/latest link. The live canonical answer must never point to unapproved newer claims. Provide a release note or concise 'what changed' description between substantive answer revisions, and link past answers with dates/dataset evidence. Test no-change runs, data-only updates, changed conclusions awaiting approval, successful human-approved publication, and rollback to the previous verified release. Keep publishing frequency independent of paid benchmark collection.

## Hosting preference: absolute minimum ongoing cost (operator direction)
The owner prioritizes the **cheapest practical public hosting**, and is open to Cloudflare. Evaluate **Cloudflare Workers with Static Assets (Free)** as first choice, **Cloudflare Pages (Free)** as alternative, and **Firebase Hosting** only as fallback. Official Cloudflare docs (2026) recommend Workers for new applications, with free/unlimited static-asset requests and no additional static-asset storage charge, subject to published static file and deployment limits. Pages similarly supports no-cost static delivery; Firebase has free transfer/storage quotas but paid overage exposure. Verify current official pricing and service-specific limits immediately before proposal. Do not place Cloudflare in front of a separately billed Firebase origin unless a clearly justified reason remains: an extra origin adds maintenance and possible bandwidth cost.
- Prefer **single-origin Cloudflare-hosted static assets** plus Cloudflare DNS, TLS, CDN, custom hostname. The protected GCS results bucket, collector jobs, and any scheduled publisher remain separate and private. A GCP weekly publication job can deploy sanitized static artifacts to Cloudflare after distinct approval; no Cloudflare account or token may be presumed available.
- Critically test **slashless canonical URLs** already emitted by Step 025/026. Cloudflare Pages route matching commonly redirects folder index routes to a trailing slash; Workers Static Assets offers `assets.html_handling` configuration. Verify actual requested URL, response status/Location, trailing slash policy, Google canonical, breadcrumbs, dated editions, 301 alias rules, CSS and sitemap on the selected service. Prefer simple documented settings or a proven static build-path solution over Worker request code; do not introduce a chargeable per-request Worker just to compensate for a URL mismatch without approval. Make a firm, tested decision on trailing slash vs slashless URLs before deployment; if the canonical strategy must change, revise with explicit migration/redirect plan preserving existing immutable published links (no historic pages have yet been published).
- Static redirect/header files can be generated from the existing Step 026 `redirects.json` plan (`_redirects`, `_headers`) only if supported and tested; no orphaned archive routes. Keep unknown route 404 behavior (avoid accidental SPA fallback), appropriate `noindex` for empty metrics, HTTPS and security headers.
- Quantify anticipated **monthly fixed hosting cost, transfer/request costs, storage/file counts, deployment quotas, domain renewals, and weekly publishing execution costs** separately, including any free-tier assumptions and practical failure modes. Put the actually *charged* amounts into the independent project cost ledger when verified; never treat a theoretical $0 free-tier hosting price as proof of total project spend.
- No hosting, DNS migration, Cloudflare account access, access tokens, new billing relationship or public launch without fresh scoped explicit approval. The implementation should first build and validate offline, compare Cloudflare Workers Static Assets versus Pages behavior, and stop at the approval boundary.
