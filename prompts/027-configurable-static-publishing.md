# Step 027 — Configurable daily/three-day static publishing, gated cloud release

**One micro-step.** Add a deliberately minimal operating path to regenerate and, **only after fresh explicit approval**, serve the Step 026 immutable question pages to web users. Do not touch collector cadence, paid API scheduling, existing GCS record immutability or benchmark security controls. **Do not purchase/register a domain or assume DNS credentials.**

## Product and operational requirements
- Benchmark collection is independently scheduled every 15 minutes **only during separately approved windows**; page publishing may run daily, every 2–3 days or weekly. Default **once daily at 02:00 UTC after the prior complete UTC day**, with an easy config for a 3-day interval. A scheduled trigger must not generate a fresh release unless the input dataset changed AND data completeness/quality checks pass. Do not infer a full 24-hour sample from a partial day; preserve previous latest on missing/failed data. No self-triggered OpenAI calls.
- Choose a simple, low-cost static host and document comparison with available GCP options, considering private source bucket vs public read-only assets, CDN/DNS, and operational overhead. Public output should contain **only sanitized immutable summary stats/pages**, never raw attempt records, claim objects, API keys, source prompt text, provider request IDs, or private bucket access. Do not make the results bucket public. Minimize billable always-on services; prefer existing build pipeline/managed static service where justifiable. No persistent SQL, Redis or web VM.
- Offline Phase 0: implement a reproducible publication runner from an explicit local/authorized snapshot input, with clear config `frequency: daily | every_3_days | weekly`, UTC as-of dates, dry-run validation, publish-only-if-changed, immutable dated releases and stable alias promotion, useful run history/logging, and an emergency “disable publishing” switch. No access to cloud by default. Tests include schedule/timezone/DST boundaries, skipped/late runs, identical data, partial/missing source, cleanup isolation, failed stage/promotion, and previous/latest continuity. Demonstrate full local end-to-end preview. If actual deploy is not necessary to prove behavior, stop after local validation and present exact plan for approval.
- **Approval A (separate, user in-session):** low-cost hosting resource configuration and private-access-to-read-only-public-artifacts design, IAM/deploy path, staging public preview with **no paid LLM request**. No additional resources until A approved. Verify public files do not disclose forbidden fields, and that private source bucket and collector stay private. Document rollback and estimated recurring charges.
- **Approval B (separate, user in-session):** enable production public publishing and scheduled regeneration only after reviewing staging; specify the final website hostname/domain, DNS/canonical URL strategy, actual cadence and limits. On uncertainty about domain/DNS or third-party account control, stop before production rollout and report exact manual approval/action required. Avoid silently enabling public serving or daily paid resources.
- Update `gcloud.md` with exact verified resources/IAM/cost/rollback **only if cloud is actually changed**. Preserve the 023 pilot's post-window `audit` then `stop` handoff, independent of publication work. Add observation/failure monitoring for publication without spamming repeated pages on missing data. **No auto-generated editorial assertions or SEO keyword stuffing.**

## Yoast-style release checks and controlled answer updates
Keep the deployed product a **static HTML publishing website**; use Yoast-inspired checks as a CI/reporting standard, **not WordPress or Yoast runtime integration**. Apply per-page checks for query intent, title/slug/meta-description relevance, natural on-page terminology, answer-first readability, breadcrumb and internal link integrity, structured data consistency, sitemap/canonical/robots alignment, and real measurement provenance. Distinguish machine-verifiable checks from editorial human review. Do not chase arbitrary SEO “green light” scores or generate spammy near-duplicate question variants.

**Two independent update lanes:** (1) scheduled **data refresh** (daily/every-three-days/weekly) updates validated numbers/figures without silently changing human-authored conclusion or `answer_revision`; (2) **editorial answer revision** after human review changes the answer/recommendation if new data warrants it, creates an immutable dated revision, and atomically promotes the canonical/latest link. The live canonical answer must never point to unapproved newer claims. Provide a release note or concise 'what changed' description between substantive answer revisions, and link past answers with dates/dataset evidence. Test no-change runs, data-only updates, changed conclusions awaiting approval, successful human-approved publication, and rollback to the previous verified release. Keep publishing frequency independent of paid benchmark collection.
