## Design constraint — simplest durable store

Use existing **GCS object storage** rather than per-request Cloud SQL and avoid speculative full storage abstraction/framework. The new component owns a versioned **single-document** record, e.g. `v1/requests/<UTC-date>/<attempt-uuid>.json`, with deterministic canonical JSON serialization. One object includes an explicit schema_version, environment (`prod` vs `test`), stable attempt UUID, timestamp in UTC, record provenance (origin cloud/region, provider/model, profile/workload/cache policy, provider request ID if available), request-level facts and all observations. Never store prompt text, generated output, API keys, database credentials, headers, raw provider errors, or unsanitized diagnostics. Preserve failure outcomes with unknown tokens/costs as JSON null rather than fabricated zero. Prices and their provenance must be representable without inventing any source not available in the existing record.

1. **Shape and validation:** implement concise Python module(s), likely `llm_metrics/object_results.py`, containing a pure record-builder/serializer, validator, and a narrow object-store interface. Reuse existing storage fact constraints where sensible; don't duplicate an entire ORM, invent new measurement keys, or modify existing SQL table schemas. Document object naming/identity, UTC timestamps and versioning, canonical encoding and how existing requests/observations map to and from the document. Explicit duplicate semantics: object key derived from stable request UUID, first successful create wins; retries of same identical object are idempotent, conflicting payload for same key is an error, not an overwrite. Concurrent jobs cannot overwrite each other. Do not put the provider request ID alone in the object key.
2. **Atomic/immutable write:** implement production-quality GCS writer using a maintained Google Cloud client library if justified; add hash-pinned packages following repo dependency conventions, and avoid changing production image unless the new component actually needs that dependency there. Use server-side create-only precondition (`if_generation_match=0` or equivalent), one-object atomic upload, and integrity/read-back checks as appropriate. Distinguish a transient failure before the server creates the object from an ambiguous acknowledged-late upload: safely reconcile by reading/verifying the exact existing object, never create a second attempt file or silently overwrite. Cap storage retry attempts/backoff; **storage retry is not model-provider retry**. Use restricted, fixed bucket and prefix configured explicitly; refuse missing target or unsafe bucket/prefix; avoid exporting a public URL. Define fail-closed errors and sanitized messages with no secrets or raw content.
3. **No paid path integration:** do **not** modify `real_benchmark.run()` to accept GCS in Step 021, change `_check_cloud_db_url()`, change provider construction, run a real provider, remove the DB preflight, change `benchmark.run_attempt()` persistence, or attach cloud IAM. This module is a testable prerequisite for a later GCS-backed execution path. Keep existing SQLAlchemy/Alembic and Docker behavior unchanged.
4. **Reading/restore for later analytics:** provide one small read/validate path for records. Demonstrate offline that one stored object can be read back into request facts + observations without loss of: date/IDs, profile/workload, region, cache provenance, output cap, actual tokens, TTFT/latency/throughput, price fields, nullable failure fields. Describe how future collection aggregation will merge objects for time windows and how the two older CSV snapshots (018f/020) might later be imported without rewriting or corrupting originals; do **not** implement a bulk ETL or public dashboard yet.
5. **Cost/scale and safety:** document realistic object counts and rough storage/write/read costs for one model running every **15 minutes (96/day, ~2,880 in 30 days)**, one-hour initial validation (24/day), and eventual four models (384/day); be clear these are estimates to recheck before cloud activation. Show lack of always-on database cost, expected per-object overhead, lifecycle/retention, and what could go wrong between paid response and successful object write. A GCS preflight alone **cannot mathematically guarantee** post-response storage succeeds; explicitly identify this remaining risk and propose the narrow next-step mitigation (e.g. durable execution record / retry-safe idempotent writer and bounded failure reporting). Do not call a write durable until GCS confirms creation or matching existing object. Target cloud + model budget under $10/day.
