# Step 014a — Flask foundation without product behavior changes

## Goal

Begin the Step 014 production-web refactor by replacing the hand-written stdlib HTTP routing/server boundary with a small Flask application foundation, while preserving the existing Metrics product behavior and keeping measurement/analytics/storage independent of Flask.

This is **014a only**. Do not try to complete the entire web refactor in one commit. HTML may remain generated by the existing rendering functions in this substep; moving HTML into Jinja templates is planned for 014b.

## Engineering quality requirement

Before editing code, read and follow `CODING_GUIDELINES.md`. It applies to this step and all future work.

Treat the Google Python Style Guide as the primary style reference where it fits this repository. Produce production-quality code that is straightforward for both human engineers and AI coding agents to understand and modify safely. In particular:

- use descriptive names and small, single-responsibility functions;
- keep dependency direction and module responsibilities explicit;
- add concise Google-style docstrings where a function/module contract is not obvious;
- comment non-obvious invariants, measurement semantics, security constraints, and architectural reasons — explain **why**, not line-by-line syntax;
- do not add noisy comments to self-explanatory code;
- never leave comments that depend on chat context or become false when implementation details move;
- update/remove stale comments as part of the refactor;
- prefer readable explicit code over clever or prematurely generic abstractions.

Review the changed code for these qualities before committing. Passing tests is necessary but not sufficient.

## Why now

`llm_metrics/dashboard.py` has grown into a large module that mixes HTTP routing, query parsing, analytics/query orchestration, and HTML rendering. That was appropriate for the dependency-free prototype. LLM Metrics is now moving toward a maintainable public production product, so the web boundary should use a real web framework before UI/product work expands further.

The architecture we are moving toward incrementally is:

```
Browser / API client
        ↓
Flask routes/controllers
        ↓
application / analytics functions
        ↓
storage
        ↓
SQLite now; production database later
```

Benchmark collection must **not** depend on Flask.

## Requirements

### 1. Introduce Flask deliberately

Add Flask as the first intentional runtime dependency for the web product.

Use a minimal, pinned/reproducible dependency declaration appropriate to the current repo. Do not add Django, FastAPI, SQLAlchemy, Gunicorn, frontend frameworks, asset pipelines, or unrelated packages in this step.

Update bootstrap/developer instructions so a fresh checkout can install what is needed predictably.

Document that D001 (standard-library first) has now earned an exception: Flask provides clear value for the production web boundary.

### 2. Add a Flask application factory

Create a small application factory such as:

```python
create_app(...)
```

Do not create a giant global Flask application with hidden import-time database work.

The factory should make testing easy and should preserve the existing database path/config behavior.

Keep configuration explicit and small. Do not build a configuration framework.

### 3. Move HTTP routing to Flask

Preserve the existing user-visible routes and query semantics, including at least the current dashboard, request-level view, and spend view.

Flask should own:
- route dispatch,
- request/query parameter access,
- HTTP status/response construction,
- 404/invalid-request behavior where appropriate.

Do not rewrite the product behavior merely because Flask makes it easy.

Existing analytics/storage functions should continue to be the source of data. Do not duplicate SQL inside Flask routes.

### 4. Preserve rendering for now

014a is about the **HTTP/framework boundary**, not visual redesign.

It is acceptable for the existing HTML-building/rendering functions to remain temporarily. Route functions may call them.

Do not spend this step converting all HTML to Jinja. That is 014b.

However, structure the Flask routes so that 014b can replace the renderer without changing analytics/storage behavior.

### 5. Preserve safety and environment semantics

Preserve all current distinctions between simulated/test and real/prod data.

Do not expose secrets, prompts, generated responses, provider error bodies, stack traces, or API keys.

Keep the server bound to `127.0.0.1` by default for local development.

Do not enable Flask debug mode by default. Do not expose the Werkzeug debugger.

Do not weaken existing validation of window/data/query parameters.

### 6. Preserve developer contract

`./run.sh` must remain the one-command local developer path.

It must still:
- run the full tests,
- seed/use simulated data as currently intended,
- start the local dashboard,
- never make a paid/network provider request.

The explicit real-provider smoke command remains separate and unchanged in paid-call semantics.

### 7. Keep benchmark/data layers framework-independent

Do not import Flask from:
- benchmark measurement logic,
- providers,
- pricing,
- storage,
- percentile/analytics primitives.

The web application may depend on those modules; they must not depend on the web application.

This dependency direction is a core requirement.

## Tests

Add/convert focused tests using Flask's test client for the HTTP boundary.

Cover at least:
- dashboard route success,
- requests route for simulated and real populations,
- spend route,
- existing valid window/metric/data query behavior,
- invalid query handling/status behavior,
- unknown route / 404,
- no network/provider call from web tests,
- app factory can use an isolated temporary database,
- no import-time server start or DB side effect,
- `./run.sh` remains simulated and working.

Preserve all existing measurement, storage, migration, cache, reliability, cost, workload, origin, and provider tests.

## Scope exclusions

Do **not** in 014a:
- move all HTML into Jinja templates (014b),
- redesign CSS/UI,
- create a frontend SPA,
- add Bootstrap/Tailwind/React,
- add a REST API redesign,
- add provider/model coverage,
- add scheduling,
- add benchmark workload matrices,
- add PostgreSQL or SQLAlchemy,
- add Gunicorn or production deployment,
- deploy to cloud,
- add authentication,
- add price scraping/history,
- change Step 013 metric/cache semantics,
- make paid API calls.
