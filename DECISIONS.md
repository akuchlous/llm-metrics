# Design decisions

## Engineering principles

Treat every commit as public.

Priority: **correctness → security → readability/maintainability → simplicity → minimal code**.

> Write the smallest implementation that is easy to understand, test, modify, and operate safely.

Prefer clear code over fewer lines. Avoid duplication, speculative abstractions, unnecessary dependencies, configuration, and future-proofing. Add structure only when current requirements justify it.

Apply the same rules to documentation and prompts: concise, non-repetitive, scoped, and easy to maintain. Put shared rules here; prompts should reference them rather than repeat them.

Every step must preserve `./run.sh`, keep secrets/runtime artifacts out of Git, and pass independent review before the next step. Future local web servers bind to `127.0.0.1` by default.

## Decisions

- **D001 — Standard library first.** Add dependencies only when they provide clear value. _Step 014a: first earned exception: Flask for the production web boundary (D056). Measurement, providers, pricing, storage, and analytics stay standard-library only._
- **D002 — `unittest`.** Dependency-free tests for now.
- **D003 — No packaging yet.** Run with `python -m llm_metrics`.
- **D004 — Minimal provider interface.** `stream(prompt, max_output_tokens)` yields text chunks (`str`) then exactly one `Usage(input_tokens, output_tokens)`; plus `name`, `model`. _Revised in Step 010: was `stream(prompt)` yielding text only; usage is reported as a final stream item, as real APIs do. Revised in Step 012a: `Usage` and `ProviderFailure` carry an optional `provider_request_id` (default `None`; see D048). Step 013: `Usage` also carries optional `cached_input_tokens`, and providers declare a `cache_policy` (default `provider_default`; see D052–D053)._
- **D005 — TTFT timer.** `time.perf_counter()` from request start to first yielded token.
- **D006 — Plain dict results.** `provider`, `model`, `metric`, `value` (unit fixed by `metric`, see D035); round only for display. _Revised in Step 009: key was `value_ms`._
- **D007 — Safe environment default.** Unset `APP_ENV` means `test`; `prod` is the other valid value.
- **D008 — No implicit real spend; never substitute dummy data.** `APP_ENV=prod` with `./run.sh` or `python -m llm_metrics` still refuses to run. Real requests happen only through the explicit `python -m llm_metrics.real_smoke` (D044). _Revised in Step 012: was "production disabled until a real provider exists"._
- **D009 — Secrets only from the environment.** The OpenAI key is read from `OPENAI_API_KEY` at call time; it is never committed, printed, logged, stored, or included in error messages or `repr`. No `.env` loading; `.env` stays git-ignored. _Revised in Step 012: previously no secrets existed._
- **D010 — CLI exit codes.** `0` success, `2` configuration error.
- **D011 — `./run.sh` is the local contract.** Keep it working after every step.
- **D012 — Venv without pip.** `run.sh` creates `.venv` with `--without-pip`, which avoids Debian's `python3-venv` package (missing on some Chromebooks). _Revised in Step 014a: dependencies are now installed by `scripts/install_requirements.py`, which uses the venv's pip if present and otherwise a pinned, hash-verified pip zipapp (D057)._
- **D013 — Use venv Python directly.** No shell activation required.
- **D014 — Respect explicit `APP_ENV`.** `run.sh` defaults to `test` only when unset.
- **D015 — Isolated run-script test.** End-to-end test runs in a temporary copy.
- **D016 — SQLite at `data/llm_metrics.db`.** Standard-library `sqlite3`; repo-root-relative; `data/` ignored.
- **D017 — One `observations` table.** `id`, `recorded_at`, `environment`, `provider`, `model`, `metric`, `value`. `environment` separates simulated and future production data. _Revised in Step 009: `value_ms` renamed to `value` because throughput is not in milliseconds; storing it under `value_ms` would have made the schema lie._
- **D018 — Initialize and upgrade on connect.** `CREATE TABLE IF NOT EXISTS` is idempotent; schema changes use `PRAGMA user_version` with ordered in-place upgrades in `storage._upgrade` (no framework). A database newer than the code is refused. All upgrade steps and the version bump run in one `BEGIN IMMEDIATE` transaction. _Revised in Step 009: previously no migrations; version 1 renamed `value_ms` → `value` and keeps all rows. Revised in Step 010: upgrades made transactional; version 2 added `requests` and `observations.request_id`. Step 012a: version 4 adds `requests.provider_request_id` (`ALTER TABLE ADD COLUMN`, NULL for existing rows). Step 013: version 5 adds `requests.workload_id`, `origin_cloud`, `origin_region` the same way; version 6 adds `cache_policy` (existing rows set to `unknown`) and `cached_input_tokens` (NULL)._
- **D019 — UTC save timestamp.** `recorded_at` uses sortable ISO 8601 UTC text.
- **D020 — `LLM_METRICS_DB_PATH` override.** Used mainly to isolate tests.
- **D021 — Persist only successful measurements.** Dynamic SQL values use parameters.
- **D022 — Fixed simulated history window.** Seeded TTFT history covers 2026-10-23 00:00 to 2026-10-29 23:00 UTC, hourly, from a fixed random seed. Fully reproducible; it does not move with the current date. Live measurements keep the save time (D019).
- **D023 — Idempotence via unique index.** `UNIQUE (recorded_at, environment, provider, model, metric)` plus `INSERT OR IGNORE` for seeding. Created with `CREATE UNIQUE INDEX IF NOT EXISTS`, so Step 003 databases gain it without a migration. Live inserts stay plain `INSERT`.
- **D024 — Seeding is test-only.** `python -m llm_metrics.seed_history` requires `APP_ENV=test` and writes only `environment = 'test'` rows. `./run.sh` runs it (idempotently) before the live measurement in `test` so a fresh clone has a meaningful graph, and never in `prod`.
- **D025 — Dashboard uses only the standard library.** `http.server` plus a server-rendered SVG chart; no web framework, no JavaScript, no charting library. The smallest justified dependency was none: adding one would require pip in `.venv` (D012) and a network install on first run. _Superseded in Step 014a for the HTTP layer by D056 (Flask); pages still render server-side with an inline SVG chart, no JavaScript, no charting library._
- **D026 — Dashboard binds to `127.0.0.1` only.** The host is a constant, not configurable. Pages send a strict `Content-Security-Policy` (no scripts or external loads). _Step 014a: unchanged under Flask (`web.HOST`); the CSP is now added to every response, including 404/405/500 error pages. Step 014b: CSP tightened to `default-src 'none'; style-src 'self'` (D058)._
- **D027 — Dashboard shows simulated TTFT for a selected time window.** Filtered to `test` / dummy / `ttft`, ordered by `recorded_at`; the x-axis is proportional to real time and spans the window. _Revised in Step 007: originally showed all rows with no window so the fixed seeded week stayed visible; real time windows replaced that, and old seeded data may now fall outside them._
- **D028 — `LLM_METRICS_PORT`.** Default `8000`; `0` picks a free port. The real bound URL is printed after binding, which lets tests run `./run.sh` without port conflicts.
- **D029 — `./run.sh` ends by serving the dashboard.** Tests → seed (test only) → measurement → dashboard (`exec`, Ctrl+C stops). A failed test or measurement (including `prod`) stops before the dashboard starts. _Step 014a: dependencies are installed (or confirmed up to date) before the tests; the dashboard command is now `python -m llm_metrics.web`._
- **D030 — Nearest-rank percentiles.** p50/p95/p99 use rank `ceil(p·n/100)` on sorted values, computed in integer arithmetic in `percentiles.py` (no HTML). Always an observed value, order-independent, deterministic for small n; preferred over interpolation because it never reports a latency that was not measured.
- **D031 — Time windows relative to current UTC.** `24h`, `7d`, `30d` via `/?window=`; bounds `now − window <= recorded_at <= now`, both inclusive (future-dated rows excluded). Filtering happens in SQL in `load_observations`. Default `7d` because hourly data then gives ~168 samples, enough for nearest-rank p99 to differ from the maximum. Any other value, empty value, or repeated `window` returns HTTP 400 listing valid choices; the value is not echoed.
- **D032 — `total_latency` metric, single pass.** Total response latency is stored with metric name `total_latency` (milliseconds): from the same request start as TTFT until the stream is fully consumed. `measure_request()` invokes the provider once and returns all results (renamed from `measure_latency()` in Step 009); TTFT semantics are unchanged. Both rows are saved in one transaction with the same `recorded_at`; if the stream fails, neither is saved. The dummy provider waits `inter_token_delay_s` (default 20 ms) between tokens so the two metrics differ.
- **D033 — Dashboard metric selector.** `/?metric=ttft|total_latency` (default `ttft`, the established headline metric) alongside `window`. Unknown, empty, or repeated values return HTTP 400, as for `window` (D031); input is never echoed. Each link keeps the other current selection.
- **D034 — `output_chunks_per_s` throughput.** Output throughput after the first chunk: `(non-empty chunks − 1) / (time of last non-empty chunk − time of first non-empty chunk)`, in chunks per second. A chunk is one non-empty item yielded by `provider.stream()` (for the dummy provider, one simulated token); it is not an API/tokenizer token count, and a real provider must keep that meaning or use a new metric name. Excluding the first chunk's wait keeps throughput independent of TTFT. Not recorded when undefined (fewer than 2 non-empty chunks, or zero elapsed time). Same single pass and transaction as D032. _Step 013: kept unchanged for continuity; its display label is now "Output chunk throughput" (D049 adds the preferred token throughput)._
- **D035 — Metric catalogue.** `llm_metrics.latency.METRICS` maps each metric name to its display label and unit (`ttft`, `total_latency`: ms; `output_chunks_per_s`: chunks/s). The name fixes the unit; never store a different unit under an existing name. The CLI and dashboard read labels and units from it. Total latency is listed first (primary user-facing latency; TTFT is diagnostic) — _ordering added in Step 010_. _Step 013: adds `output_tokens_per_s` (tokens/s), listed before `output_chunks_per_s` so token throughput is shown first._
- **D036 — Request records with own identity.** Each measured request is one `requests` row: `id` (random UUID hex, llm-metrics' own identity, never a provider API request ID), `recorded_at`, `environment`, `provider`, `model`, `input_tokens`, `requested_max_output_tokens`, `output_tokens`, the effective prices, and the costs. Its metric observations keep the `observations` table and reference it via `request_id`; the request and its observations share `recorded_at` and are written in one transaction (`save_request`). Token counts and costs are request facts, not `metric/value` rows, because they are not per-metric measurements and would make metric queries misleading. Observations from before Step 010 and simulated history have `request_id` NULL: nothing is fabricated for them. UUIDs (not integers) so requests from different databases can later be merged without collisions. _Revised in Step 011: a `requests` row is now any benchmark attempt (successful or failed), with `outcome`; see D040–D041._
- **D037 — Token accounting from provider usage, never from chunks.** `input_tokens` and `output_tokens` come only from the provider's `Usage`; chunk counts never become token counts. `requested_max_output_tokens` (the cap the benchmark asked for; CLI `MAX_OUTPUT_TOKENS = 64`) is stored separately from `output_tokens` (what was generated). Measurement fails if usage is missing or repeated, or output exceeds the cap. The dummy provider uses a **simulated** tokenizer (`ceil(len(text) / 4)`, deterministic, matches no real provider) and stops before exceeding the cap. _Step 013: `output_tokens_per_s` added (D049), using provider-reported output tokens and the D034 timing boundary; still never derived from chunk counts._
- **D038 — Prices in one place; cost stored with its basis.** `llm_metrics/pricing.py` holds all prices (USD per 1M tokens, keyed by provider+model; dummy: simulated $2.00 input, $8.00 output). `input_cost = input_tokens × input_per_1m / 1e6`, `output_cost` likewise, `total_cost` = sum; stored unrounded (REAL), rounded only for display. Each request stores the effective input/output rates used, so its cost stays explainable after an in-code price change; there is no price-history service. (`gpt-6-luna` standard $0.10 / $0.50 per 1M, verified 2026-10-30 by the project owner and against OpenAI's official pricing documentation, `https://developers.openai.com/api/docs/pricing`.) _Revised in Step 012: `PRICE_PROVENANCE` records each real price's official source and verification date (`None` = not yet verified). Step 012a: source changed to the official documentation URL (the old `openai.com/api/pricing/` page refuses automated reads); rates unchanged._
- **D039 — Individual request view.** `/requests` lists the 20 most recent `test` requests (newest first): time, request id, total latency (primary), TTFT (diagnostic), chunk throughput, input/output/max tokens, total/input/output cost, provider/model; labelled simulated. The aggregate dashboard (`/`) is unchanged, including its `ttft` default metric.
- **D040 — Every attempt is persisted with an outcome.** One attempt = one provider call (no retries). `requests.outcome` is `success` or a stable internal failure category: `timeout`, `rate_limited`, `provider_error`, `transport_error`, `invalid_response` (`outcomes.py`). Providers raise `ProviderFailure(category)`; future adapters map native HTTP/SDK errors to these categories at the provider boundary, and analytics never depend on provider wording. Contract violations detected by measurement (no text, usage missing/repeated/before text, output above the cap) are `invalid_response`. Any other exception is an llm-metrics bug and is not recorded as a provider failure. No error messages, stack traces, prompts, or secrets are stored. The CLI exits 0 for a recorded failed attempt. _Step 012: request/configuration errors (HTTP 400/401/403/404 → `RequestRejected`) are not provider failures and are not recorded._
- **D041 — Unknown is NULL, never zero; failures keep no partial metrics.** For a failed attempt `input_tokens`, `output_tokens`, and all costs are NULL (prices and `requested_max_output_tokens` are still known and stored), and no observations are saved: TTFT or chunks seen before the failure are discarded, so latency/throughput distributions stay success-only without query changes. `failed_after_ms` (request start → failure detected) is recorded only for failures and is never `total_latency`. A table CHECK enforces success ⇔ known facts and NULL `failed_after_ms`; failure ⇔ NULL facts and non-NULL `failed_after_ms`. Schema version 3 rebuilt `requests` (SQLite cannot drop NOT NULL) in the upgrade transaction; Step-010 rows became `success`, unpaired observations are untouched.
- **D042 — Observed benchmark success rate.** Population: all `requests` rows (attempts) for the environment/provider/model with `now − window <= recorded_at <= now`. `success_rate = successes / attempts`, `failure_rate = failures / attempts`, shown with the attempt count and failures by category; no attempts → no rate. Observations without a request (pre-Step-010, simulated history) are not attempts. It is what our runner observed, not provider uptime. Latency/throughput percentiles use successful observations only.
- **D043 — First real provider: OpenAI `gpt-6-luna` via the Responses API, standard library only.** `openai_provider.OpenAIProvider` sends one `POST /v1/responses` with `stream: true`, `max_output_tokens`, `store: false`, and no tools, using `urllib` (no SDK: avoids pip in `.venv` (D012) and hidden SDK retries). SSE `response.output_text.delta` → text chunks; `response.completed` usage (or `response.incomplete` because `max_output_tokens` was reached) → final `Usage`. Errors map to Step-011 categories at this boundary: HTTP 429 → `rate_limited`; 408/504 and socket timeouts → `timeout`; other 5xx, `response.failed`, `error` events, other incomplete reasons → `provider_error` (`error` with a rate-limit code → `rate_limited`); connection/read errors → `transport_error`; malformed events or usage → `invalid_response`. Since Step 013 the request also sends `prompt_cache_options: {"mode": "explicit"}` with no breakpoints (D052), and `cached_input_tokens` is read from `usage.input_tokens_details.cached_tokens` (D053). Account billing errors (`insufficient_quota` / `credit_balance_exhausted`, as HTTP 429, an `error` event, or `response.failed`) are our account's problem, not the provider's: they raise `RequestRejected` and are not recorded, like HTTP 400/401/403/404. No retries. The generic provider interface did not change.
- **D044 — Real requests only by explicit command, stored as `prod`.** `python -m llm_metrics.real_smoke` requires `OPENAI_API_KEY` (refuses with no request otherwise), announces the call, makes exactly one attempt with a fixed harmless prompt and `max_output_tokens = 64`, stores it with `environment = 'prod'`, and prints a summary without the prompt, response, or key. The price is looked up before the call. `prod` means real-provider data; `test` means simulated. Pages show one population at a time with distinct labels (TEST / SIMULATED DATA vs REAL PROVIDER DATA). Tests and simulated paths make no network calls.
- **D045 — Benchmark API Spend.** `/spend?window=` (default 30d) shows, from `prod` attempts only, per provider + model: successful paid calls, input/output tokens and total cost summed over successful attempts (stored values), and failed attempts counted separately with cost unknown (never $0; a group with no success shows "unknown"); plus a grand total of known costs. Computed at query time from request rows; no materialized aggregates. It is llm-metrics' own API token spend, not provider revenue, user cost, infrastructure cost, or a normalized price comparison.
- **D046 — Sanitized local diagnostics for provider failures.** `ProviderFailure` and `RequestRejected` carry `diagnostics`: which code path failed (`http_status`, `event:response.failed`, `event:error`, `event:response.incomplete`, `stream_read`, …), HTTP status, OpenAI `x-request-id`, error `code`/`type`/`param` (for stream `error` events read from the nested `error` object when present, never the event's own type), incomplete reason, exception class name. Every value must be a short `[A-Za-z0-9_.:-]` token or becomes `<redacted>`; HTTP error bodies are read (≤ 64 KB) only to extract those fields. Never messages, bodies, headers, prompts, response text, or the key. Printed only by `real_smoke --debug`; never stored. The stored outcome category is unchanged. Added after the first live call failed as `provider_error` with no way to tell which of four paths caused it; they then showed the cause of later failures (`insufficient_quota` / `credit_balance_exhausted`, see D043). Kept as the minimum needed to understand future provider failures; diagnostics never become analytics categories.
- **D047 — Explicit `reasoning.effort = "none"` for the benchmark request.** The official model page (`https://developers.openai.com/api/docs/models/gpt-6-luna`, checked 2026-10-30) lists `reasoning.effort` values `none`, `low`, `medium` (default), `high`, `xhigh`, `max`. The benchmark sets `none` explicitly so this first latency benchmark measures simple, inexpensive text generation instead of silently using the `medium` default (reasoning tokens are billed as output and count against the 64-token cap). _Step 012a: replaces the Step-012 follow-up basis (third-party docs); now officially documented, and the successful live call used it._
- **D048 — Provider request id beside our own request id.** OpenAI's `x-request-id` response header is stored as nullable `requests.provider_request_id` (schema version 4) for successful and failed attempts, when it is a short `[A-Za-z0-9_.:-]` token (otherwise NULL, never `<redacted>`). It travels as an optional field on `Usage` / `ProviderFailure`. Relationship: llm-metrics `requests.id` (our UUID, the identity) ↔ `provider_request_id` (diagnostic metadata for asking OpenAI about a request; never a key, never a replacement). `real_smoke` prints it. Chosen over the response's `resp_…` id because it exists on HTTP errors as well, and with `store: false` a response id cannot be looked up later. NULL when unknown: simulated runs, connection failures, failures detected only by measurement (e.g. stream ended without a final event), and rows recorded before Step 012a (not backfilled). No tracing service or abstraction.
- **D049 — `output_tokens_per_s`: observed effective generation throughput.** For a successful attempt, `Usage.output_tokens / (time of last non-empty chunk − time of first non-empty chunk)` in tokens/s: the provider's authoritative output token count over the same client-observed generation interval as `output_chunks_per_s` (D034), so TTFT is excluded. Omitted, never 0 or infinity, when the denominator is not defensible (fewer than 2 non-empty chunks, zero elapsed time) or no output tokens are reported. Semantics and limits: the token count covers the whole response (including any tokens in the first chunk, and reasoning tokens, which OpenAI counts as output) while timing is observed at the client stream boundary (network and buffering included), so it reads high for very short responses and is not a claim about internal GPU decoding speed. Computed provider-agnostically in `measure_request`; for the dummy provider the tokens come from the simulated tokenizer and are labelled simulated. Real-provider views show it before chunks/s. Not backfilled for older attempts.
- **D050 — `workload_id`: stable benchmark-case identity.** Every new attempt stores a non-empty `requests.workload_id` naming what test was run (not the provider/model or the result): `simulated.default.v1` (`python -m llm_metrics` / `./run.sh`: prompt "Say hello.", cap 64) and `smoke.short_text.v2` (`real_smoke`: fixed short prompt, cap 64, streaming, `store: false`, `reasoning.effort: none`, prompt caching disabled). `smoke.short_text.v1` was the same request without the cache control; it was bumped to v2 when the cache control was added (no v1 attempt was recorded). A plain versioned string; a change to the prompt, cap, or request shape gets a new version. `run_attempt` requires it (keyword-only, no default) and `save_request` refuses an attempt without it. No workload table, registry, JSON, tags, or prompt text. Rows from before schema version 5 stay NULL (unknown): they could be labelled by environment, but the real workload was not stable (the first real attempt was sent without `reasoning.effort`), so labelling them would be guessing.
- **D051 — Measurement origin as explicit configuration.** Every new attempt stores `requests.origin_cloud` and `origin_region`: where the benchmark runner executed, not the provider's serving region. Set by `LLM_METRICS_ORIGIN_CLOUD` / `LLM_METRICS_ORIGIN_REGION`; unset or empty means `local` / `unknown` (deterministic for development). Values must match `[a-z0-9]([a-z0-9-]{0,61}[a-z0-9])?` (e.g. `aws` / `us-east-1`, `gcp` / `us-central1`); an invalid value is a configuration error (exit 2, not echoed) before any request. Never inferred from IP, geolocation, or cloud metadata services. Stored as plain request columns so later aggregate filters can use them without schema redesign; no origin comparison views yet. Rows from before schema version 5 stay NULL.
- **D052 — Requested cache policy as a request fact; OpenAI smoke runs with caching disabled.** `requests.cache_policy` records what the request asked of the provider's prompt/prefix cache, from a fixed vocabulary (`providers.CACHE_POLICIES`, enforced by a column CHECK): `disabled` (a documented provider control establishing no cache reuse was sent), `enabled` (cache reuse explicitly allowed/requested), `provider_default` (no cache control sent), `unknown` (cannot be established: every attempt before schema version 6). Each provider declares the policy its requests carry (`LLMProvider.cache_policy`, default `provider_default`), and `run_attempt` stores it, so the stored value cannot drift from the request body; new attempts may not record `unknown` or values outside the vocabulary. `OpenAIProvider` sends `prompt_cache_options: {"mode": "explicit"}` with no `prompt_cache_breakpoint` and records `disabled`. Evidence: the official prompt caching guide (`https://developers.openai.com/api/docs/guides/prompt-caching`, section "GPT-5.6 and later", checked 2026-10-30): "Set `prompt_cache_options.mode` to `explicit` to use only developer-selected breakpoints" and "When no explicit breakpoints are placed, the request does not use prompt caching or create cache writes"; its single-turn example puts `prompt_cache_options` at the top level of a GPT-6 Responses request. The gpt-6-luna model page lists `prompt_caching` as supported but does not name this field; if the model rejected it, the request would fail with HTTP 400 (`RequestRejected`, not recorded, `--debug` shows `error_param`). The simulated provider sends no cache control: `provider_default`. Prompts are not randomized to defeat caches (workload comparability first). Different cache policies are different populations: `load_observations(..., cache_policy=...)` restricts a metric population to one policy without schema change; no cache comparison views yet.
- **D053 — `cached_input_tokens` only from provider usage; 0 ≠ NULL.** `requests.cached_input_tokens` (nullable INTEGER, CHECK ≥ 0) comes only from the provider's authoritative usage: for OpenAI `usage.input_tokens_details.cached_tokens` (part of `input_tokens`), carried as optional `Usage.cached_input_tokens`. `0` means the provider explicitly reported zero; NULL means not reported, failed attempt, or recorded before schema version 6. Never inferred from latency, repeated prompts, chunk timing, or cost. A reported value that is not an integer count within `input_tokens` makes the attempt `invalid_response`. Cache-write tokens are not stored, and costs still price all input at the standard rate (a cached read would be overstated; with caching disabled none is expected).
- **D054 — Cache terminology.** User-facing text uses evidence-based terms: **uncached / cold-ish** = the request used a disabled cache policy and/or the provider reported 0 cached input tokens; it is not a claim that every internal provider/model/GPU cache was cold. **cached / warm** = the provider reported cached input tokens > 0, or the benchmark deliberately used an enabled policy. `provider_default` and `unknown` stay visible as such and are never labelled cold. "Hot"/"cold" are not used as provable provider states.
- **D055 — Google Python style, checked by Google's own tools.** All Python (package and tests) follows the Google Python Style Guide as applied by `CODING_GUIDELINES.md`: module-only imports (`from llm_metrics import storage`, `import datetime`; names only from `typing`/`collections.abc`), imports grouped and sorted (isort `google` profile), 80-column lines, 4-space indentation, Google-format docstrings (`Args:`/`Returns:`/`Raises:`/`Yields:`/`Attributes:`) where a contract is not obvious, and comments that state current invariants rather than step history (schema-version notes in `storage.py` are migration documentation and stay). Formatting is `pyink` (Google's formatter) configured in `pyproject.toml`; linting uses Google's unmodified `pylintrc` committed as `.pylintrc` (Apache 2.0, header kept). Both are development tools only: nothing is installed into `.venv` or needed at runtime (D001, D012). `inconsistent-quotes` is disabled on the command line: on Python 3.12+ pylint counts the inner quotes of f-string expressions (e.g. `f"{row['id']}"`), which must differ from the outer quotes for Python 3.10 support, and Google style allows the other quote character to avoid escaping. Justified inline exceptions: `__main__` (module name required by `python -m`), `do_GET` (method name required by `http.server`), and `unsubscriptable-object` in two test modules (they subscript `load_request` results for ids they just saved).
- **D056 — Flask is the HTTP boundary; dependencies point inward.** `llm_metrics/web.py` owns route dispatch, query parameter access, HTTP status codes and headers, and serving; it contains no SQL and no HTML. `llm_metrics/dashboard.py` is the application/view layer: it validates already-parsed query parameters (`{name: [all values]}`, so repeated and blank values are still rejected), loads data through `storage`, and returns view data (rendered by templates since 014b, D058). _Step 014c: `dashboard` now gets its data from `analytics` (D059); the direction is `web → dashboard → analytics → storage`._ Direction: `web → dashboard → storage`; `web.py` is the only module that imports Flask or Werkzeug, and measurement, providers, pricing, storage, and analytics never import the web layer (enforced by an AST test and a fresh-process import test). `create_app(db_path=None)` is an application factory: no import-time app, database, or server work; the database path is read when the app is created (default `config.get_db_path()`) and opened per request. Routes, query semantics, page content, and status codes are unchanged (200 / 400 with valid choices, value never echoed / 404); GET only, so other methods now get 405 instead of the standard library's 501. Debug mode is forced off even if `FLASK_DEBUG` is set, so the Werkzeug debugger and stack traces are never exposed; unhandled errors return a generic 500 and are logged server-side. `python -m llm_metrics.web` binds the socket itself on `127.0.0.1` (so a busy port keeps the clear "already running" message) and hands it to Werkzeug's single-threaded development server; production serving (Gunicorn etc.) is out of scope until deployment.
- **D057 — Pinned, hash-checked dependencies installed by `run.sh`.** `requirements.txt` pins Flask 3.1.3 and every transitive dependency (Werkzeug 3.1.9, Jinja2 3.1.6, itsdangerous 2.2.0, click 8.5.0, blinker 1.9.0, MarkupSafe 3.0.4) with the sha256 of every published file, each version at least two weeks old when chosen. `scripts/install_requirements.py` (standard library only) installs with `pip install --require-hashes --only-binary=:all: --isolated`, so only those exact wheels can be installed and nothing is built from source. If the venv has no pip, it downloads pip's official zipapp at a pinned version (26.2.1), verifies its sha256 before running it, and discards it, so no `python3-venv`/`ensurepip` or sudo is needed. A stamp in the venv records the installed requirements' sha256: the network is needed only on the first run and after `requirements.txt` changes. Tests stay offline: installer tests mock pip and downloads, and the `run.sh` end-to-end test copies the already-provisioned venv into its temporary repository. Tests therefore run under the project venv (`.venv/bin/python -m unittest`), not the system Python.
- **D058 — Presentation in Jinja templates; Python prepares view data.** `dashboard.py` builds no HTML: each page has a pure `*_view(...)` function (explicit inputs) and a `load_*_view(db_path, ...)` wrapper that loads its data (through `analytics` since 014c, D059), returning plain dictionaries of display-ready values (formatted numbers, "—" for unknown, "unknown" for unknown cost, link targets, chart coordinates). `web.py` chooses the template and calls `flask.render_template` through one helper, `web.render_page(template, view, status)`, so Jinja, like Flask, stays inside the web layer and `dashboard` imports neither. Templates live in `llm_metrics/templates/`: `base.html` (document shell, stylesheet link, view navigation, simulated/real data label), `aggregate.html`, `requests.html`, `spend.html`, `invalid_query.html`, plus partials `_aggregate_nav.html` (metric/window links shared with the invalid-query page), `_chart.html` (SVG), and `_macros.html` (one `nav_links` macro for the four link lists). Templates only loop, branch on prepared booleans/None, and print values: no storage access, percentiles, costs, reliability, population decisions, cache inference, or arithmetic. **Chart:** geometry (scales, coordinates, label positions, polyline points) is computed in Python (`dashboard._chart`); `_chart.html` places precomputed numbers in SVG elements, keeping the chart readable as markup without putting calculations in a template. **CSS:** moved to a static file, `llm_metrics/static/dashboard.css`, served by Flask at `/static/dashboard.css`, which let the CSP drop `'unsafe-inline'`: it is now `default-src 'none'; style-src 'self'` (no inline styles, scripts, or external resources). **Escaping:** Flask's Jinja autoescaping covers every value; no template uses `|safe`, `Markup`, or `{% autoescape %}` (enforced by a test), and a test renders HTML-special characters in every stored free-text field. Visible page text is unchanged except product copy no longer mentions development step numbers.
- **D059 — Analytics return natural values; the dashboard owns presentation.** `llm_metrics/analytics.py` interprets stored facts for any consumer: window bounds from a duration, `load_metric_window` (a metric's successful observations as `Observation(recorded_at: datetime, value: float)`, their `MetricSummary` with nearest-rank `percentiles: {50: …, 95: …, 99: …}`, and `outcomes.success_rate` over all attempts), `load_recent_attempts` (storage rows with `recorded_at` as an aware datetime), `spend_totals`/`load_benchmark_spend` (real environment only; `total_cost` None when no cost is known). Results are floats, ints, aware datetimes and None, never display strings. Population rules live in its module and function contracts: success rates count every attempt, distributions use successful observations only, simulated and real environments are never mixed, spend is real-provider only and never counts unknown cost as $0. `dashboard.py` owns query semantics (valid values, window names → durations, which population each page shows) and view preparation (number/currency/percent formats, "—" and "unknown", UTC display times, links, labels, chart SVG geometry); it never reads `storage` or computes statistics. Direction: `web → dashboard → analytics → storage`, enforced by an AST test (`dashboard` may not import `storage`; `analytics` may not import `dashboard` or `web`; `storage` imports neither) and by fresh-process tests that `analytics` loads without Flask/Werkzeug/Jinja/MarkupSafe. Representation: frozen dataclasses (`Observation`, `MetricSummary`, `MetricWindow`, `SpendTotals`, `Spend`) for the new results crossing the boundary, because their fields (raw vs. successful-only populations, None for unknown cost) must be unambiguous; the existing, tested `outcomes.success_rate` dict and `storage` row dicts are kept as is. No base classes, registries, or service objects.
